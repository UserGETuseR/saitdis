# Чайная история · подключение к 1С

Документ для директора и 1С-специалиста. Описывает, что веб-приложение уже
отдаёт, что нужно получить от стороны 1С и в каком порядке включать обмен.

## Что уже работает без 1С

- Заказы, движения склада и остатки хранятся в PostgreSQL. Источник истины — сервер.
- Закрытие заказа (статус «Готов») одной транзакцией списывает остатки и создаёт
  документы движения в `chay_inventory_movements`. Продажа не может остаться без
  движения товара, и наоборот.
- Каждое изменение попадает в очередь `chay_integration_outbox` с ключом
  идемпотентности. Очередь переживает перезапуск и повторяет неуспешную отправку
  с растущей задержкой.
- Пока доступ к 1С не выдан, обмен выключен, но события продолжают накапливаться.
  После настройки они уйдут по порядку — ничего не теряется.
- Администратор видит состояние очереди и может проверить связь с 1С из кабинета
  (раздел «Связь с 1С»).
- Секреты 1С не хранятся ни в браузере, ни в базе приложения — только в окружении
  сервера (`/etc/chay-api.env`, режим `0600`).
- В каждом событии передаётся `branchId`: `sochi`, `rostov`, `krasnodar`, `moscow`.

## Соответствие данных

Позиция заказа сопоставляется со складом по коду каталога (`catalog_id`):

| Что в заказе | Код на складе | Количество |
|---|---|---|
| Чай | `teaId` (например `shu_puer`) | граммы навески |
| Грибная добавка | `mushroomId` (например `lionsmane`) | 1 порция на позицию |
| Десерт, напиток, мерч | артикул целиком (`dessert-mochi`) или короткий код (`mochi`) | штуки |

Если позиции нет в справочнике склада или остатка не хватает, заказ всё равно
закрывается: списывается доступное количество, а расхождение фиксируется в
журнале аудита (`action = order_stock`) и передаётся в событии полем
`stockShortages`. Это сделано осознанно — касса не должна останавливаться
из-за незаполненного справочника, но расхождение обязано быть видимым.

Отметка лояльности начисляется за напиток. Десерты и мерч отметку не дают.
Шесть отметок дают одну награду; списание награды уменьшает баланс.

## Контракт HTTP-сервиса на стороне 1С

Нужны два метода.

`GET /hs/chay/health` — возвращает HTTP 200. Используется для проверки связи.

`POST /hs/chay/exchange` — принимает событие. Обязательные заголовки:

```text
Authorization: Basic <сервисный пользователь>
Content-Type: application/json
Idempotency-Key: <уникальный ключ события>
X-Event-Type: <тип события>
X-Integration-Source: chay-web
```

Повторный запрос с тем же `Idempotency-Key` не должен создавать второй документ.
Ответ 2xx считается успехом, любой другой код — поводом для повтора.

```json
{
  "event": "order.changed",
  "entity": { "type": "order", "id": "ord_a1b2c3" },
  "payload": {
    "id": "ord_a1b2c3",
    "branchId": "sochi",
    "userId": "usr_...",
    "userName": "Анна",
    "phone": "+79000000000",
    "status": "done",
    "total": 1450,
    "channel": "self",
    "fulfillment": "pickup",
    "deliveryAddress": "",
    "scheduledAt": 1772000000000,
    "customerNote": "",
    "items": [
      { "kind": "tea", "sku": "TEA-shu_puer", "teaId": "shu_puer", "name": "Шу пуэр", "grams": 100, "quantity": 100, "unit": "g", "price": 900 },
      { "kind": "dessert", "sku": "DESSERT-mochi", "name": "Моти", "quantity": 2, "unit": "pcs", "price": 550 }

```

Также приходит `order.created` — при оформлении заказа гостем.

### Событие склада

```json
{
  "event": "inventory.movement",
  "entity": { "type": "inventory", "id": "mov_ord_a1b2c3_shu_puer" },
  "payload": {
    "movementId": "mov_ord_a1b2c3_shu_puer",
    "branchId": "sochi",
    "catalogId": "shu_puer",
    "type": "sale",
    "quantity": -100,
    "stockBefore": 480,
    "stockAfter": 380,
    "orderId": "ord_a1b2c3",
    "documentRef": "ord_a1b2c3",
    "createdAt": 1772000000000
  }
}
```

Типы движений: `receipt`, `writeoff`, `sale`, `stocktake`, `correction`,
`transfer_in`, `transfer_out`. Знак `quantity` отражает направление:
отрицательное значение — расход. Событие `inventory.changed` приходит при
изменении карточки позиции (название, единица, минимальный запас).

## Что нужно получить от стороны 1С

1. Название конфигурации: 1С:Розница, 1С:УНФ, 1С:Управление торговлей или иная.
2. Версия конфигурации и версия платформы 1С:Предприятие.
3. Где расположена база: локальный сервер, 1С:Фреш или сервер подрядчика.
4. Тестовая база или её копия. На боевой базе разработку обмена не начинаем.
5. HTTPS-адрес тестовой публикации и IP/домен, с которого разрешены запросы.
6. Сервисный пользователь с минимальными правами. Не логин директора или кассира.
7. Контакт 1С-разработчика, который поднимет HTTP-сервис и подтвердит структуру объектов.
8. Справочники: номенклатура, характеристики, единицы, склады, типы цен,
   контрагенты, дисконтные карты — выгрузка или описание.
9. Соответствие городов складам и организациям 1С. Для старта обязательно Сочи.
10. Какой документ создаётся из веб-заказа и на каком статусе: заказ покупателя,
    чек ККМ, реализация или другой.
11. Кто источник истины по остаткам, ценам, гостям и бонусам.
12. Частота обмена, часовой пояс, правила возврата и отмены.
13. Три тестовых сценария с ожидаемым результатом: заказ, отмена, изменение остатка.

## Порядок ввода в работу

1. Заполнить справочник склада: код каталога каждой позиции должен совпадать с
   тем, что ожидает 1С. До этого шага расхождения будут попадать в `stockShortages`.
2. Утвердить карту данных и владельца каждого справочника.
3. Поднять HTTP-сервис в тестовой базе 1С.
4. Прописать доступ в `/etc/chay-api.env` и перезапустить сервис:
   `systemctl restart chay-api`.
5. Проверить связь: раздел «Связь с 1С» в кабинете, кнопка «Проверить соединение».
6. Пройти сценарий: заказ → закрытие → отмена → повтор события без дубля.
7. Сверить суммы, НДС, единицы и остатки.
8. Сделать резервную копию и только затем включать боевой обмен.

Живой обмен нельзя считать завершённым до получения тестового доступа и
подписания карты данных специалистом 1С. Всё остальное со стороны
веб-приложения готово и покрыто тестами.
